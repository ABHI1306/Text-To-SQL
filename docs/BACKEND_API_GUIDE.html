Authentication and session

Sign-in options

GET /api/v1/auth/methods (public) → {"local": true, "directory": bool, "sso": bool}. Use it to decide what the login page shows: the password form always (it handles local and LDAP accounts with the same fields), plus a "Sign in with single sign-on" link when sso is true.

Password login (local or LDAP)

POST /api/v1/auth/login with {"username", "password"}.

// 200
{ "access_token": "eyJ...", "token_type": "bearer", "expires_in": 900, "must_change_password": false }
  • Keep access_token in memory only (never localStorage). It lives 15 minutes.
  • The response also sets an httpOnly refresh cookie (refresh_token, path /api/v1/auth, 8 hours, rotated on every refresh). JavaScript cannot read it; just send credentials.
  • Wrong user or password → 401 with the same generic message. Five failures lock the account for 15 minutes (423).
  • must_change_password: true → the only thing the account may call is POST /api/v1/auth/change-password until it is changed. Show the change-password screen.

Single sign-on (OIDC)

Send the browser to GET /api/v1/auth/oidc/login (a full page navigation, not fetch). After the provider redirects back to /api/v1/auth/oidc/callback the backend sets the same refresh cookie. On return, call POST /api/v1/auth/refresh to obtain the first access token.

Keeping the session alive

  • On page load and whenever any call returns 401: POST /api/v1/auth/refresh (no body, cookie only) → new access_token (and a rotated cookie). Retry the failed call once.
  • If refresh fails → the session is over: clear state, show the login page ("session expired").
  • Do not fire two refreshes at once: rotating tokens mean the second one is treated as a replay and revokes the whole session. Queue concurrent 401s behind a single refresh.
  • POST /api/v1/auth/logout (204) revokes the session and clears the cookie.

Who am I → build the navigation

GET /api/v1/me (any signed-in user):

{ "user_id": "…", "username": "asha", "role": "DBA",
  "capabilities": ["ask_question", "view_audit", "…"],
  "projects": [{ "id": "…", "name": "Sales" }],
  "must_change_password": false }

Show/hide screens from capabilities, never from the role name. The API re-checks everything; the UI hiding a button is a convenience only. Role/capability changes take effect within about a minute (re-fetch /me when you get a 403 you did not expect).

Errors

Status Meaning What to do
401 Missing/expired token Refresh once, retry, else log in
403 Account lacks the capability (or must change password: detail.code = PASSWORD_CHANGE_REQUIRED) Hide/disable the action
404 Not found or not visible to you (the API deliberately does not say which) Show "not found"
409 Conflict (e.g. no deployed model yet, duplicate, deploy running) Show the message
422 Validation failed or the request was well-formed but refused Show the message
423 Account locked Show "try again later / ask a DBA to unlock"
503 A dependency is down (metadata DB, model server) Offer retry

detail comes in three shapes — handle all (see failureMessage in ui/src/adminApi.ts): 1. a string: {"detail": "Project not found"} 2. a FastAPI validation list: {"detail": [{"loc": ["body","title"], "msg": "…", "type": "…"}]} 3. a typed failure: {"detail": {"code": "UNKNOWN_COLUMN", "message": "…", "retryable": false, "errors": [...]}}

Typed failure codes (show with an E_ prefix, e.g. E_UNKNOWN_COLUMN): UNKNOWN_MODEL, UNKNOWN_COLUMN, JOIN_NOT_ALLOWED, NON_SELECT, DISALLOWED_FUNCTION, SYNTAX_ERROR, DRY_RUN_FAILED, TIMEOUT, EMPTY_RESULT, AMBIGUOUS_QUESTION, OUT_OF_SCOPE, LLM_UNAVAILABLE, POLICY_ERROR, INVALID_SQL.

Asking a question (streaming)

POST /api/v1/threads/{thread_id}/ask — capability ask_question; you must own the thread.

// request
{ "question": "Top 5 customers by revenue last quarter", "max_rows": 1000, "preview_as": null }

max_rows 1–10000 (default 1000; the server may lower it further). preview_as (user id) is only for accounts with rerun_sql; the run is audited and not saved to the thread.

Read it with fetch, not EventSource

EventSource cannot send the Authorization header. Use fetch and read response.body as a stream, splitting on blank lines. A working parser is parseSse in ui/src/askStream.ts.

event: intent
data: {"intent":"data_question","standalone_question":"…","used_context":false,"ms":412}

event: retrieval
data: {"models":["orders","customers"],"pairs":[],"instructions":[],"ms":88}
…

Every step event also carries ms (that step's time); the UI timeline shows each value and the sum.

Event contract (in this order; steps repeat on correction)

Event Payload When
intent {intent, standalone_question, used_context} after classification (and follow-up rewrite)
retrieval {models[], pairs[], instructions[]} after retrieval
sql_candidate {logical_sql, attempt} each generation / correction
compilation {ok, errors[], sql?} after each compile. sql (compiled, physical SQL) only for accounts with rerun_sql
validation {ok, errors[{code, message, identifier?, suggestions[]}]} after each validation
correction {attempt, reason} before each retry
rows {columns[], rows[][], truncated, row_count} after execution
answer_token {text} summary text (and replies for non-data intents)
chart {vega_lite_spec} optional, after the answer
suggestions {items[]} up to 3 follow-up questions
clarification {question, options[]} when the intent is "clarify" — show as quick replies
done {thread_id, message_id, latency_ms, tokens, gpu_ms, policy_context, attempts, prompt_version} terminal success
error {code, message, retryable} terminal failure (typed). Exactly one terminal event (done or error) ends every stream

Notes: - intent values: data_question, clarify, respond (chit-chat / out of scope). - answer_token currently arrives as one chunk, not token-by-token; append text as it comes. - tokens is 0 and gpu_ms is null for now (not yet measured) — do not rely on them. - Show the logical SQL to everyone (it uses business names); the compiled SQL only when present. - Validation errors before the request starts come back as normal HTTP errors (404 thread not found, 422 bad body, 403 preview_as without the capability, 409 no deployed model), not as events. - If the stream is cut mid-way with no terminal event, treat it as a failure and offer retry.

Related calls

  • POST /api/v1/projects/{id}/threads → 201 {"id": "<thread_id>", "project_id": "…"} (create one per conversation; reuse for follow-ups so the backend can resolve "and in 2024?").
  • GET /api/v1/threads/{thread_id} → {"id","project_id","owner_id","messages":[{"id","question","standalone_question","logical_sql","answer","created_at"}]}. Readable by the owner, by accounts with view_all_threads, or by someone it was shared with.
  • POST /api/v1/messages/{message_id}/feedback {"rating":"up"|"down"} → 201 {"id","rating","proposal": {…}|null}. Use the message_id from the done event. Thumbs-up proposes the question+SQL as a pair for DBA review.
  • POST /api/v1/threads/{thread_id}/rerun-sql {"logical_sql", "max_rows"} (capability rerun_sql) → {"logical_sql","sql","columns","rows","truncated","row_count"} or a typed 422/503 failure.
  • The older POST /projects/{id}/query (single JSON answer) and /query/stream still work with the previous event names; new work should use the thread endpoint.

Dashboards, saved questions and sharing

  • A saved question stores logical SQL (POST /projects/{id}/saved-questions {question, logical_sql, chart_spec?}; the SQL must compile for you or you get 422).
  • A dashboard holds up to 24 tiles; each tile pins one of your own saved questions. PUT /dashboards/{id}/tiles replaces all tiles — always send the full list: {"tiles":[{"saved_question_id","chart_spec"?,"position":{…},"refresh_schedule"?}]}. layout and position are free-form JSON owned by the UI (e.g. grid x/y/w/h).
  • Results are always per viewer. GET /dashboards/{id}/tiles/{tile_id}/result and GET /saved-questions/{id}/result compute rows under the caller's own data access, so two people viewing the same shared dashboard can see different numbers. Do not cache results across users in the UI. Response: {"columns","rows","truncated","cached","computed_at","policy_context","chart_spec","question"}. cached: true only means the server reused an identical-access result (default 5 min). Query ?max_rows= (1–10000).
  • POST /dashboards/{id}/refresh (owner) clears cached results; re-fetch the tiles afterwards.
  • Opening a dashboard needs ownership or a share and the view_shared capability. GET /dashboards/{id} → {id, project_id, owner_id, title, layout_json, created_at, tiles[], is_owner}; use is_owner to show edit controls. Anything you cannot see is 404.
  • Sharing: POST /shares {resource_type: "dashboard"|"saved_question"|"thread", resource_id, grantee_type: "user"|"role", grantee_id}. For grantee_type: "user" use the user id; for "role" use the role name (e.g. "Analyst"), not its id. Only the owner can share, list (GET /shares?resource_type=&resource_id=) or revoke (DELETE /shares/{id}). Revoking takes effect immediately. Shares are read-only; a viewer must also be a member of the project.
  • GET /shared-with-me → [{share_id, resource_type, resource_id, title, owner_id, granted_at}]. Open a dashboard with GET /dashboards/{resource_id}, a saved_question with its /result. (Opening a shared thread uses GET /threads/{resource_id}.)

Scheduled questions

  • Create: POST /scheduled-questions {saved_question_id, schedule, timezone} (capability schedule_question, you must own the saved question).
  • schedule is a preset (hourly, daily, weekly) or a 5-field cron string. Anything firing more often than every 15 minutes is refused (422 with the reason). timezone is an IANA name (default UTC).
  • Object: {id, project_id, saved_question_id, schedule, timezone, status, paused_reason, next_run_at, last_run_at, last_status, failed}. status is active or paused; failed is true when the last run failed (show a failure state). paused_reason examples: paused_by_owner, owner_unavailable, owner_lacks_access.
  • POST …/{id}/pause (204), …/resume (200, returns the object), …/run-now (runs immediately as you; send an Idempotency-Key header so a double-click is one run), DELETE (204).
  • GET …/{id}/runs → last 20 runs [{id, slot, started_at, finished_at, status ("succeeded"|"failed"), policy_context, row_count, error, trigger ("schedule"|"manual")}].
  • Runs execute as the owner. If the owner is disabled the job pauses itself. A failed run adds a notification for the owner.

Notifications

GET /notifications?limit=50 → [{id, kind, payload, created_at, read_at}], newest first (any signed-in user, own only). kind is scheduled_run_failed or drift_report. Mark one read with POST /notifications/{id}/read (204). There is no push channel yet — poll (e.g. on navigation).

Audit browser

GET /audit-events query: actor_id (UUID), action, resource_type, resource_id, since, until (ISO datetimes; since must be before until), limit (1–200, default 50), cursor.

{ "items": [{ "id": 981, "actorId": "…", "action": "login_failed", "resourceType": "user",
              "resourceId": "…", "details": {…}, "createdAt": "2026-10-16T09:12:44+00:00" }],
  "nextCursor": 931 }

Newest first. For the next page pass cursor=<nextCursor>; nextCursor: null ends the list. GET /audit-events/export.csv takes the same filters (no paging), returns a CSV download of up to 10,000 rows. Fetch it with the auth header and save the blob (a plain link cannot send the token). (GET /audit is the same endpoint under its earlier name.)

Evaluation

POST /projects/{id}/eval/run (send an Idempotency-Key; same key = same run) → 202 {run_id, status, created}. Poll GET /eval/{run_id} every few seconds while run.status == "running"; it ends as completed or failed (run.error). The body is {run: {id, status, summary, error, …}, results: [{case_id, question, outcome, stage, failure_code, latency_ms, …}], diff: {previous_run_id, regressions[], fixes[], unchanged}}. summary has execution_accuracy, correct, scored, failures_by_stage, latency_seconds. GET /eval/{run_id}?format=markdown returns the report as Markdown text for download.

Other response shapes worth knowing

  • GET /projects → {"items":[{"id","name","setup_step"}]}; setup_step is complete or the wizard step to resume.
  • GET /projects/{id}/setup → {"project_id","step","selected_tables":[…]}.
  • GET /projects/{id}/catalog/tables?search=&schema=&page= → {"items":[{"schema","table", "approx_rows","column_count", …}],"page":…}.
  • GET /roles → {"items":[{"id","name","description","is_system","capabilities":[…]}]}.
  • GET /projects/{id}/drift-reports → {"items":[{"id","mdlVersion","hasDrift","summary","findings", "draftMdlVersion","createdAt"}],"nextCursor"} (cursor = last item's createdAt). Drift endpoints use camelCase; most other newer endpoints use snake_case — follow each endpoint's shape exactly.
  • Knowledge: pairs {id, question, logical_sql, status, source, proposed_by, decided_by, created_at, decided_at}; instructions {id, text, active, created_by, updated_at}.
  • GET/PUT /settings/allowed-hosts → {"hosts":[…],"source":"database"|"environment"}; the PUT body is {"hosts":[…]}; link-local / cloud-metadata addresses are refused (422).

Conventions

  • Idempotency: send an Idempotency-Key header on run-now and evaluation runs.
  • Pagination: cursor-based (cursor + limit); nextCursor: null = last page.
  • Row limits: the server enforces a ceiling on max_rows; results carry truncated: true when cut.
  • Request ids: handle responses defensively; do not depend on undocumented fields.
  • Unknown fields are rejected (422) on most request bodies — send only documented fields.
